# Backend contract

## Delhi road alerts (local Phase 1 review + Phase 2 matching; no AWS route deployed)

The manually curated Delhi Traffic Police source adapter accepts a normalized document, not an assumed live API. `GET /v2/road-alerts` is public and returns `{alerts: PublicRoadAlert[]}` with a fixed public field allowlist: source links, headline, stated cause/location, source and validity times, availability, freshness, state, `resolutionState`, and a road ID/review time only for reviewed outcomes. A current, unique, unreviewed match may include `proposal: {displayLabel, method, confidenceCategory, explanation}`. It is explicitly unverified and has **no candidate road ID**. Ambiguous, unlocated, stale, invalid-source-point, and out-of-coverage results have `proposal: null`. Public alerts never expose candidate IDs, full source text, importer errors, reviewer identity/reason, resident report details or private photos. Imported and ambiguous alerts remain `Reported / Unverified` and do not mark roads blocked. Source availability does not imply road coverage.

`POST /v2/road-alerts/import`, `GET /v2/road-alerts/review`, `GET /v2/road-alerts/{id}` and `PATCH /v2/road-alerts/{id}/review` require a validated `varuna-responder` access session. The import body is `{canonicalSourceUrl, advisoryUrl?, sourceIdentifier?, sourceType, publishedAtText?, retrievedAt, originalHeadline, originalText, statedCause?, affectedLocation?, validFromText?, validUntilText?, sourceAvailability, sourceError?, locationHints?}`. `locationHints` may include `roadNames`, `roadReferences`, `intersection` (two names), `landmarks`, `localities`, `geometryVersion`, or `coordinates` with `coordinateSourceUrl` matching the source link. Import is idempotent for identical source/link and content; changed content under an existing ID returns 409 for explicit re-review. The protected detail/list additionally contains original text, `candidateRoads` with road ID, contextual display label, matching method/evidence, distance and ambiguity margin where relevant, confidence category, source/context link, snapshot geometry version, legacy reason/confidence, `matchAmbiguity`, `resolutionState`, source error and review audit. Result states are `matched_candidate`, `ambiguous`, `unlocated`, `outside_coverage`, `stale_snapshot`, `invalid_source_location`. Review body is `{decision: "confirm_flood_blockage" | "clear" | "reject", reason, road?}`. Confirmation requires a current flood-related source and a candidate `RealRoadReference` whose point is uniquely validated against the versioned 84-way snapshot. `clear` applies only to that confirmed alert. A clearance returns condition to Unknown, never Low or Safe. Multiple independent current confirmations must all be resolved before a road is eligible again. The route-eligibility gate is internal and no real-road route recommendation endpoint is exposed. `/v1` Scenario and photo-report APIs are unchanged.

Resolver priority is exact OSM name/reference, reviewed alias, explicit shared-node intersection, reviewed landmark plus locality, source-linked point within 25 m, then reviewed landmark geometry within 60 m. An ambiguous higher-priority tier is not silently overridden by a lower tier. A source point outside the query box or invalid WGS84 range cannot be used to locate the alert. The pinned context file and its required source/review trail are described in [`frontend/src/data/README.md`](../frontend/src/data/README.md); mismatched snapshot versions fail closed. There is no geocoder, source polling, automatic import or cloud persistence. Deployment of these routes requires a separate authorization, retention, quota and source-permission review.

`nearRoadNames` is an additional `locationHints` list for named-road **context**, not a direct road target. When the named OSM way is within 120 m of a reviewed landmark point, the resolver considers that context at the same priority as locality; the proposed unnamed way must still lie within 60 m of the landmark point. Original headline/text and stated location can supply an exact sourced name; cause and source timestamps are retained for review/freshness, never used as invented coordinates.

## Separate real-road v2 contract (implemented locally, not deployed)

The feature preview uses a **static**, manually exported OSM road snapshot and does not call the Scenario endpoints to render Delhi. The existing `/v1/*` API and its synthetic IDs remain unchanged for `main`; its photo reports are never joined to OSM ways. `types.ts` declares separate `RealRoadReference`, `RealRoadReportDraft`, `RealRoadReport`, and `RealRoadEvidence` shapes. The handlers work locally but are **not yet deployed**; when `/v2` is unreachable, the preview remains explicitly read-only.

`GET /v2/roads` returns the limited OSM FeatureCollection plus `metadata.geometryVersion` (`sha256:<digest>` of the exact source JSON), 12 m match tolerance, and 5 m minimum separation from the next closest way. Public `GET /v2/real-road-evidence` returns `{evidence: [...]}` with only current, responder-reviewed `Confirmed Blockage` or `Cleared` observations. Its explicit field allowlist is road ID, snapped point, review state and decision, observation/review/expiry times, and source. Pending Review, Rejected, and expired records never appear; neither do report ID, note, owner/reviewer identity, image key, or photo URL. Pending records are available only through responder-authorized report endpoints; the submitting resident receives confirmation directly from the create response. The browser must use the server's versioned snapshot for any submission, never a synthetic or stale copy. `POST /v2/real-road-reports/upload-url` takes `{idempotencyKey, contentType, sizeBytes}` with a validated Cognito access token and returns the same signed multipart POST shape as `/v1`; the S3 policy enforces 1 byte to 8 MB. `POST /v2/real-road-reports` takes `RealRoadReportDraft`, requires the same user-derived upload key, decodes and strips image metadata, then validates the proposed OSM way and WGS84 point server-side. Stale versions, points outside the query box, points farther than 12 m from the selected way, and points within 5 m of another way are rejected. Observations must be current (at most 24 hours old, never future); omitted `capturedAt` uses submission time. No browser user ID is trusted.

New evidence starts `Pending Review` and never changes road status. The create response (including an idempotent retry) is only `{id, reviewStatus}` so a submitter cannot retrieve private report or reviewer details through that route. `GET /v2/real-road-reports`, `GET /v2/real-road-reports/{id}`, and `PATCH /v2/real-road-reports/{id}/review` require `varuna-responder`; detail alone returns a 60-second private photo URL. Review body is `{decision: "confirm_blockage" | "clear" | "reject"}`. Confirmed Blockage applies only until `evidenceExpiresAt` (24 hours after observation); Cleared returns condition to Unknown and does not certify safety. `expiresAt` for private metadata is seven days after creation, with DynamoDB TTL and explicit filtering before TTL deletion; S3 raw uploads expire after one day and private JPEGs after seven. The v2 table also records an atomic per-user UTC-day cap of 10 upload-form requests. The capability URL is short-lived and should not be shared. No flood depth, prediction, route advice, automatic ingestion, or `/v1` report migration is included.

The JSON schemas define the wire shape for `Segment` and `Report`. [`types.ts`](types.ts) defines the response types for TypeScript consumers. Coordinates are `[longitude, latitude]` in WGS84. Scores are ordinal 0–1 indicators, not water depth or flood probability. `null` means missing data; it must never be interpreted as zero.

## Read endpoints

| Request | Response |
| --- | --- |
| `GET /v1/pilot` | Pilot metadata, synthetic flag, segments, drains, default route query |
| `GET /v1/snapshots/current?mode=Scenario` | Versioned risk snapshot; `Live` returns 503 in fixture mode |
| `POST /v1/routes/compare` | `snapshotId`, `originNodeId`, `destinationNodeId`, `travelMode` → candidate paths and recommendation |
| `POST /v1/interventions/compare` | Same route fields plus `selectedRouteId` → two ranked simulated actions |

`Closed` is a road status separate from the numeric risk class. `Pending Review` belongs to a report and cannot influence risk until accepted. `Simulated` belongs to an intervention result and never overwrites the baseline snapshot. Scenario data is always labelled `Scenario` and has a synthetic provenance string.

## Integration sequence

1. Call `GET /v1/pilot`. It returns `segments` (each with a two-point `geometry` array), `drains`, `routeQuery`, `bundleVersion`, and `synthetic: true`.
2. Call `GET /v1/snapshots/current?mode=Scenario`. It returns `id`, `mode`, `computedAt`, `weather`, and a risk entry for each `segmentId`. Match those IDs to pilot segments. A risk entry has `class`, `roadStatus`, `score`, `coverage`, `features`, `missingFeatures`, `evidenceIds`, and `isClosed`.
3. Compare routes with the current snapshot ID:

   ```json
   {"snapshotId":"<current snapshot id>","originNodeId":"N-2-0","destinationNodeId":"N-2-4","travelMode":"Pedestrian"}
   ```

   The response includes `fastestRouteId`, `recommendedRouteId`, `reason`, and `candidates`. A candidate includes `geometry` (WGS84 GeoJSON `LineString`), `segmentIds`, `travelMinutes`, `exposure`, `unknownShare`, `highestClass`, and `blocked`. A null route ID means no route was found. When no meaningful lower-exposure alternative exists, `reason` says so; the fastest route is not a safety claim.
4. Compare interventions using the same query plus the selected route:

   ```json
   {"snapshotId":"<current snapshot id>","originNodeId":"N-2-0","destinationNodeId":"N-2-4","travelMode":"Pedestrian","selectedRouteId":"R1","drainIds":["D-01","D-02"]}
   ```

   The response contains two ranked `results`, each with `simulated: true`, a before/after exposure, affected segment classes, and the drainage assumption. Render the baseline separately.

If the snapshot changes after review or closure, the previous ID returns `409 stale_snapshot`; refresh before route or intervention calls. `Live` returns `503 mode_unavailable` in fixture mode. All error bodies use `error.code`, `error.message`, `error.retryable`, and `error.requestId`.

## Photo reports and local-only closures

Both `POST /v1/reports/upload-url` and `POST /v1/reports` require a Cognito access token from a signed-in account, including a newly self-registered resident account during the temporary hackathon sign-up period (the local adapter uses a loopback-only demo session). The first takes `{idempotencyKey, contentType, sizeBytes}` and returns `{uploadUrl, uploadFields, imageKey, expiresAt, maxBytes}`. POST a multipart form to `uploadUrl`, appending every returned field followed by the `file` field; do not set the multipart Content-Type header yourself. S3's signed policy enforces a 1-byte to 8-MB content-length range, exact key and MIME type. Then create the report with that image key and idempotency key, pilot segment/point, optional note and capture time. The authenticated subject is bound server-side to both steps; browser-supplied user IDs are ignored. Supported types are JPEG, PNG and WebP, up to 8 MB/20 megapixels; the backend also checks size and decodes/re-encodes a private JPEG review copy without EXIF. New reports are always `Pending Review`, have `analysis.provider: none`, and do not affect risk.

`GET /v1/reports` returns metadata without photo URLs. `GET /v1/reports/{id}` returns a 60-second private photo URL. `PATCH /v1/reports/{id}/review` takes `{decision: "accept" | "reject", manualVisibleWater?: "none" | "possible" | "clear" | "uncertain"}`; acceptance requires the manual value. Only `varuna-responder` members can list, view, accept, or reject reports. API Gateway validates the access token's signature, issuer, audience, expiry and `openid` scope; Lambda checks `token_use=access`, subject and group. Repeated identical submission/review is idempotent; conflicting reuse returns 409. Local report storage is in process memory; AWS mode uses S3/DynamoDB. Uploaded metadata has a seven-day `expiresAt`; expired records are excluded from list/detail/risk before asynchronous DynamoDB TTL deletion. Synthetic fixture examples do not expire.

Acceptance replays the manual observation at the fixture `validAt` for the **synthetic Scenario** only. `scenarioValidAt` is separate from actual `createdAt`/`capturedAt`; this is not evidence of current Delhi conditions. Only Accepted evidence may change `O`, route exposure and a subsequent simulated comparison. The snapshot and route contracts are otherwise unchanged. There is no AI image analysis in HTTP mode and no public photo derivative.

`PATCH /v1/segments/{id}/closure` remains local-only and memory-backed; deployed closure persistence is not part of this slice.
