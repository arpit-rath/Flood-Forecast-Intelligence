# Scenario API and private photo reports

`template.yaml` defines API Gateway, the Scenario Lambda, separate real-road evidence and official-source alert support, a private encrypted S3 bucket for report photos, and separate DynamoDB tables. It has no credentials. It does not configure Live weather, AI image analysis, Delhi-wide risk, or persistent closures. `Live` requests return 503. Packaging and building create no AWS resources. The Phase 3 schedule is disabled by default and has not been deployed by this work.

The Lambda package contains only the Python backend modules needed by the two handlers, `data/fixture/scenario.json`, the checked-in OSM road snapshot and reviewed alert context staged under `data/real_roads/`, and `requirements.txt` for boto3 and Pillow. It does **not** stage frontend code or assets. The staging script recreates `infra/.lambda-package/` from an explicit source allowlist; it refuses to replace that directory if unexpected files are present. Both staging and SAM build output are ignored by Git.

From the repository root, with Python 3.12 and AWS SAM CLI installed, build it with these exact commands:

```powershell
python infra/package_lambda.py
sam build --template-file infra/template.yaml
sam validate --template-file infra/template.yaml --lint --region ap-south-1
```

If SAM CLI is not on `PATH` but `uv` is available, use this exact alternative for the second command:

```powershell
uvx --python 3.12 --from aws-sam-cli==1.167.0 sam build --template-file infra/template.yaml
```

Inspect `.aws-sam/build/VarunaFixtureApi/` after building: it must not contain `frontend/`, `node_modules/`, tests, credentials, or `.git/`. Verify Pillow has Linux `.so` files rather than Windows `.pyd` files. If necessary, use `sam build --use-container --template-file infra/template.yaml` with Docker running. ## Public sign-up abuse and cost controls

Public sign-up means anyone who confirms an account can request upload forms and send photos; authentication alone is **not** an upload quota. The signed S3 POST caps each upload at 8 MB and binds the key/type, but a form can be reused until its short expiry and repeated uploads can still incur S3 request/transfer charges. The API's default stage throttle is 2 requests/second with burst 10, and the upload-form route has a tighter 0.5 requests/second with burst 2. API Gateway throttling is best-effort, shared across callers, and **not** a per-user or spending ceiling; it may also slow legitimate users at peak. Raw upload objects expire after one day even when the user never finishes report creation. These controls limit individual objects and exposure time, not total spend.

Before opening public sign-up, configure an AWS Budget with low email alerts for this account/project and CloudWatch alarms or a staffed dashboard for Cognito `SignUpSuccesses`/`SignUpThrottles`, API `4xx`/`5xx`/throttles, Lambda invocations, S3 request/object growth and DynamoDB consumed requests. Budget alerts can lag and do **not** stop charges. Consider Cognito user-pool AWS WAF rate rules/CAPTCHA if sign-up abuse appears; WAF has its own cost and should be tested in Count mode first. Review service quotas, billing and any existing account-level protections. The v2 table atomically limits each signed-in subject to 10 upload-form requests per UTC day, but signed forms can be reused until expiry and attackers can create many accounts; this is **not** a hard storage/spending cap. V1 has no per-user quota. Sustained abuse requires an operator to disable self-sign-up and/or upload routes promptly. Do not leave public uploads unattended.

After the event, in **Cognito user pool → Sign-up → Self-service sign-up → Edit**, disable self-registration and verify “Create an account” is no longer offered. Set `VITE_PUBLIC_SIGNUP_ENABLED=false` and rebuild/release the frontend so it says sign-in only; this browser flag never controls Cognito access. Existing users are **not** removed by the Cognito switch: review the Cognito Users list and `varuna-responder` group membership, disable suspicious or unneeded users (revoking sessions/tokens), and delete accounts only after the retention/records decision. Check the S3 bucket, DynamoDB table and billing for unexpected volume; then carry out the documented retained-resource cleanup. This post-event review is a manual operator task, not a SAM deployment side effect.

The bucket blocks public access, encrypts objects, and accepts only a signed multipart POST with an S3-enforced `content-length-range` of 1 byte to 8 MB. Raw `uploads/` expire after one day; metadata-stripped private `review/` JPEGs expire after seven days. A protected detail request returns a 60-second presigned GET URL. DynamoDB stores report metadata, server-derived owner subject, an idempotency fingerprint and a seven-day TTL (`expiresAtEpoch`). Expired records are hidden from list/detail and removed from risk **before** DynamoDB's asynchronous TTL deletion. S3 Lifecycle is also asynchronous; previously issued photo URLs can remain usable for up to their 60-second lifetime. Pending reports do not alter risk; acceptance requires a human visible-water decision and replays it at the historical fixture time in the **synthetic Scenario** only. This is not Live evidence, Delhi-wide risk, or AI analysis.

The bucket and both report tables use `Retain` on stack deletion to avoid accidental data loss. After a pilot, inspect and manually empty/delete the retained bucket and both retained tables when authorized; confirm no legal hold or records obligation first. If upgrading a table that already contains uploads without `expiresAtEpoch`, the app hides those legacy records but DynamoDB cannot TTL-delete them; inspect and manually remove or backfill them under an approved migration. Delete the separately created Cognito users, group, app client, domain and pool only when no longer needed. Neither table requests paid point-in-time recovery: this short pilot does not justify the additional cost by default. If an existing table has PITR enabled, inspect its actual post-update setting and charges instead of assuming template removal turns it off. Reassess PITR and backup/retention obligations before a longer-lived pilot. S3/DynamoDB lifecycle/TTL are not an immediate deletion guarantee.

The parser retrieves only `https://traffic.delhipolice.gov.in/en/news-alertadvisory/alerts` plus same-origin HTML details linked from its `<h2>` alert titles. It checks `robots.txt` before each bounded run, makes one listing request and at most ten new/changed detail requests sequentially, uses the same descriptive Varuna User-Agent and ten-second timeout, and refuses redirects, PDFs, social links, administrative paths and non-HTML responses. Per [RFC 9309 section 2.3.1](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1), a successfully fetched policy is obeyed; an HTTP 400–499 robots response except 429 is treated as unavailable and the **same** strict listing/detail allowlist may proceed with a non-fatal `robots_unavailable` source-health warning. A 429 defers further requests through its `Retry-After`; 5xx, network failure, malformed successful policy, uncertain rule evaluation or an applicable Disallow stops ingestion. Robots unavailability is not authorization and does not expand source scope. The adapter stores ETag/Last-Modified validators, source identifiers, text, dates when explicitly present, SHA-256 and parser version. A changed listing headline can trigger a conditional detail re-fetch and immutable revision; an unchanged listing is not a guarantee that an old detail has not changed. The adapter does **not** geocode or infer coordinates. Automatic imports begin Reported / Unverified, leave roads Unknown and cannot change `/v1` Scenario, resident reports or routing eligibility. Previous records survive source failure and carry their original timestamps; source-health state becomes stale/unavailable.

Pre-activation gate: on 11 October 2026, manual checks with the declared Varuna User-Agent observed `GET /robots.txt` → HTTP 403 (`text/html`), `GET /en/news-alertadvisory/alerts` → HTTP 200 (`text/html`), and a current same-origin alert detail → HTTP 200 (`text/html`). Those results support the RFC unavailable-robots branch but do **not** validate the deployed parser, current site policy, date/time fields, actual stack configuration or operating costs. The schedule remains `DISABLED`; manually invoke one bounded run only after a reviewed deployment, inspect its source-health warning and imported records, and verify public redaction and `/v1` regression before a separate schedule-enabling update. If a later robots response contains an applicable Disallow or is 429, 5xx, malformed or unreachable, ingestion must stop/defer as above. Do not switch User-Agent, host, social/PDF mirror or administrative route to work around a denial. A locally passing synthetic fixture is not proof of live-source compatibility.

Parser v2 repair gate: the source's alert-teaser `h2` link supplies the exact headline; the detail parser reads only labelled Drupal fields inside the alert article. A missing or contaminated body field creates a listing-headline-only record with a private `parser_warning`, and `sourceStatus.state` becomes `degraded` rather than `current`. Publication and end fields are preserved only when labelled; an end date plus clock time remains raw wording without an inferred timezone. A parser-version upgrade forces a bounded unconditional detail refetch even if the listing returns 304, creating a new immutable projection for the same raw-content hash. Previous projections and review audit remain in the retained table until TTL, but only the active projection per official detail URL is public. Confirmations do not transfer to the new projection; a still-current prior confirmation continues to constrain the internal route gate until cleared or expired.
